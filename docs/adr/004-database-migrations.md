# ADR 004 — Lightweight Plain-SQL Migration Runner for Multi-Tenant Schema Management

**Status**: Accepted  
**Date**: 2026-10-07  
**Decision makers**: Engineering & Security Architecture Team

## Context

MeetMind AI isolates tenant data in PostgreSQL using a schema-per-tenant model (`tenant_<id>`).
Initially, services attempted ad-hoc runtime table initialization using `CREATE TABLE IF NOT EXISTS`
on startup or on first request. This presented critical architectural and operational problems:

1. **Race Conditions & DDL Contention**: Concurrent worker starts would execute concurrent DDL statements,
   risking deadlocks and permission conflicts.
2. **Lack of Version Tracking**: There was no deterministic record of which schema modifications had been applied
   to which tenant schema.
3. **Privilege Violations**: The application role required DDL privileges (`CREATE TABLE`, `CREATE INDEX`)
   in request-handling paths, violating the principle of least privilege.
4. **Tooling Overhead**: Adopting Alembic would require introducing heavy Python dependencies (SQLAlchemy, Mako)
   and complex multi-tenant per-schema routing mechanics that obscure raw SQL DDL.

## Decision

We chose to implement a lightweight, zero-dependency plain-SQL migration runner located in
`backend/security/meetmind_security/migrations.py` that operates on numbered SQL migration files
in `backend/security/migrations/` (e.g. `001_initial_schema.sql`).

Key components:

1. **Per-Tenant Version Tracking**: Each tenant schema contains a dedicated tracking table:
   `_schema_migrations (version INT PRIMARY KEY, name TEXT, checksum TEXT, applied_at TIMESTAMPTZ)`.
2. **Transactional Execution**: Each migration runs inside a transaction with `SET LOCAL search_path = "<tenant_schema>"`.
3. **Checksum Verification**: Migrations are cryptographically verified using SHA-256 checksums. Modifying an already-applied
   migration file raises a `MigrationChecksumMismatchError`.
4. **Elimination of Runtime DDL**: Request-path code never executes DDL. Service startup verifies that the schema
   is at the expected version (`verify_schema_version` / `ensure_schema_current`) and applies pending migrations if configured.
5. **Defense-in-Depth Immutability**: Migrations install PostgreSQL triggers (`BEFORE UPDATE OR DELETE`) on append-only
   tables (`audit_events`, `consent_events`) and configure role permissions (`REVOKE UPDATE, DELETE, TRUNCATE`).

## Consequences

- **Pros**:
  - Zero third-party dependencies beyond existing `asyncpg`.
  - Trivial multi-tenancy: running migrations for a new tenant or all tenants is an explicit loop with schema switching.
  - Transparent SQL reviews: pure SQL migrations are readable, verifiable, and verifiable by security compliance.
  - Fail-safe startup: application rejects connections if database schemas are out-of-date.
- **Cons**:
  - Schema migrations must be authored as idempotent standard PostgreSQL scripts.
  - Rollbacks are explicit compensating forward migrations rather than automatic autogenerated downgrades.
