## 2. Mandatory Acceptance-Criteria Insertions (§6, §7, §10–§13, §16–§18)

Every downstream component specification listed below MUST incorporate the exact contract clauses in this section before acceptance sign-off.

### Clause Q-C1 (Unified T0 Clock & Monotonic Timing — Applies to §6, §7, §10, §11, §12, §13, §16, §17, §18)

> "All published `EventEnvelope` payloads MUST preserve upstream `timing` fields from `t0_capture` (capture time translated onto the Gateway server epoch clock via `clock_sync` / `clock_report`, bounded by $|\epsilon| \le \text{RTT}/2$) and call `meetmind_schemas.timing.stamp()` for every owned stage (`classify_pub`, `retrieval_done`, `card_pub`, `ui_render`), validated monotonically via `validate_monotonic()`."

### Clause Q-C2 (Latency Budget Ceilings — Section-Specific Insertions)

- **§6 Trigger Classification**: Insert into §6 acceptance criteria:
  > "`asr_pub -> classify_pub` MUST achieve `P50 <= 200 ms` and `P95 <= 300 ms` on server-clock telemetry (`docs/latency/budget.yaml`). Generative LLM API calls are **strictly prohibited** inside §6 (ADR-008); implementation MUST use deterministic rules, regex/lexicons, or local embeddings (`<= 50 ms`)."
- **§7 Agent Orchestration & §11 Live In-Meeting Strategy**: Insert into §7 and §11 acceptance criteria:
  > "Lane 0 deterministic entity/identifier chips MUST arrive `t0_capture -> ui_render <= 1000 ms` P50 / `2000 ms` P95 (using ASR `stable_prefix_words` + `trigger_candidate` before `trigger_confirmed`). Tier-1 retrieval-only `InsightCard` publication (`first_card_tier1`) MUST complete within `P50 <= 2000 ms` / `P95 <= 3500 ms` from `t0_capture` (Lane 1 UI target `1500 / 3000 ms`) with zero LLM calls. Tier-2 reasoned card revisions (`revision > 1`) MUST complete within `2000 ms` P50 / `3000 ms` P95 after `first_card_tier1` (Lane 2 `P95 <= 4000 ms` from `t0_capture`). Stage-own processing overhead excluding external retrieval/LLM API time MUST remain `<= 25 ms` P95 (`budget_check.py`)."
- **§10 Pre-Meeting Brief**: Insert into §10 acceptance criteria:
  > "Pre-meeting brief generation (`pre_meeting_brief`) MUST emit `PrefetchHint` entities and warm per-meeting `ContextCache` entries prior to `meeting_start`, propagating `trace_id` and `timing` and grounding every brief claim via `InsightCard` evidence spans."
- **§12 Post-Meeting Workflow Agents**: Insert into §12 acceptance criteria:
  > "Post-meeting summaries and action digests execute in the post-meeting lane (no real-time latency SLA), MAY consume optional accuracy-lane async transcripts (ADR-012), and MUST pass every persisted claim/decision through `verify_card()` and §8 schema validation before graph write."
- **§13 Action & Trust Gate**: Insert into §13 acceptance criteria:
  > "Tier-3 `action_recommendation` cards MUST satisfy `t0_capture -> card_pub <= 3500 ms` P50 / `5000 ms` P95. External mutations (`external_action_execution`) have zero real-time latency SLA and MUST block until explicit human approval triggers an append-only `audit_events` row and a Graph `Approval` node (`Zero Autonomous Mutation Invariant`)."
- **§16 Frontend Dashboard / Side Panel**: Insert into §16 acceptance criteria:
  > "Clients MUST render cards using `CardRevisionTracker` (highest `revision` per `card_id` wins; lower revisions dropped cleanly), render `blocks[]` with zero HTML injection, display `confidence_band` badges (`HIGH | MEDIUM | LOW`) and **never numeric percentage confidences**, label `status=inferred` alerts/suggestions visibly, and emit `ui_render` server-calibrated timestamps."
- **§17 Web Enrichment Tool**: Insert into §17 acceptance criteria:
  > "External web facts retrieved by §17 MUST carry `source_type="external"`, `uri`, quoted `span`, `retrieved_at`, and `as_of`, adhere to ZDR/regional data handling constraints in ADR-010 (no Google Search/Maps grounding for strict India ZDR tenants), and pass `verify_card()` before reaching `InsightCard.claims[]`."
- **§18 Advanced Agent Cognition Upgrade**: Insert into §18 acceptance criteria:
  > "Any §18 reasoning upgrade (speculative retrieval, contradiction detection, counterfactual checks) MUST remain subject to Clause Q-C3 (Abstention-by-Default) and Clause Q-C4 (Held-Out Golden Set Gates); improvements that increase `displayed_unsupported_claim_rate` above `0.0` FAIL CI."

### Clause Q-C3 (`InsightCard` & Abstention-by-Default — Applies to §7, §10, §11, §12, §13, §16, §17, §18)

> "Every user-visible intelligence payload MUST be a valid `InsightCard` (`meetmind_schemas.cards`) validated on both publisher and Gateway (`validate_outbound_card`). Default action on `missing_evidence`, `stale_evidence`, `conflicting_evidence`, `asr_uncertainty > 0.35`, `restricted_secret`, or `disagreement_signalled` is **`ABSTAIN`** via `meetmind_quality.policy.publish_decision`. When low ASR confidence affects a quoted figure/identifier, live display of a `verified` claim is forbidden; optional post-meeting storage MUST label the text `'heard as ...'`. `restricted=True` cards route exclusively to listeners whose role is in `visible_roles`."

### Clause Q-C4 (Golden Evaluation CI Gates — Applies to §6–§18)

> "All candidates in §6–§18 MUST pass `scripts/eval_quality.py` on the external held-out set (`EVAL_HELDOUT_PATH`, unseen during development) with `min_cases_for_claim >= 300` before release (seed sets print `NON-AUTHORITATIVE` and `INSUFFICIENT N` when `N < 300`):
>
> - `displayed_unsupported_claim_rate == 0.0` (hard gate: `0` displayed hallucinations)
> - `abstention_correctness >= 0.95`
> - `supported_claim_precision >= 0.98`
> - `HIGH`-band claim precision `>= 0.95`
>   Any pipeline regression against `RetrievalOnly` calibration checks fails CI."

## 3. Design-Only Specification Proposals (Zero Code Built in Q-0d)

### 3.1 §6 Engineering & Decision Taxonomy Additions

In addition to `docs/spec-amendments/engineering-pack.md` (12 engineering categories), §6 specification adds five decision-hygiene triggers (`spec only` in Q-0d):

1. `decision_proposed` — tentative architectural/sprint choice needing explicit confirmation or owners.
2. `assumption_stated` — unverified premise (load assumption, backward compatibility, rollout window) linked to `AssumptionNode` (`ADRs` / incidents).
3. `disagreement_signalled` — explicit dissent or contested trade-off between speakers (forces `ABSTAIN` on consensus claims).
4. `owner_unassigned` — action item or deployment step agreed without an identified participant owner.
5. `approval_required` — proposed mutation (production deploy, PR merge, incident severity escalation, ticket transition) requiring Trust Gate sign-off.

### 3.2 §8 Decision Genome Graph Schema v2 (Q8 Contract)

§8 specification is updated to bind directly to `meetmind_schemas.graph` (ADR-011):

- **13 Nodes**: `Statement`, `Claim`, `Evidence`, `Assumption`, `Decision`, `Approval`, `Action`, `Outcome`, `Meeting`, `Participant`, `Entity` (`Ticket | PullRequest | Deployment | Incident | Service`), `Commitment`, `RiskFlag`.
- **10 Edges**: `SAID_IN`, `ASSERTS`, `SUPPORTED_BY`, `ASSUMES`, `LED_TO`, `APPROVED_BY`, `OWNED_BY`, `EXECUTED_AS`, `RESULTED_IN`, `REFERENCES`.
- Reuses `InsightCard.claim_id` and `Evidence.source_id` verbatim, isolates tenant namespaces via `tenant_node_label()`, and stores `expected_outcome` (`metric`, `target`, `review_date`, `owner`) + `required_approvers` + lifecycle `status` on every `Decision`.

### 3.3 §11 / §12 Decision-Quality Signals (Under Abstention Policy)

Live (§11) and post-meeting (§12) agents specify six **Decision-Quality Signals**, each published ONLY as an `alert` or `verified` `InsightCard` that clears `verify_card()` and `publish_decision()` (never overriding abstention when transcript evidence is uncertain):

| Signal                         | Condition Detected                                                                                            | Mandatory Evidence / Abstention Rule                                                  |
| :----------------------------- | :------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------ |
| `unresolved_disagreement`      | Conflicting `Statement` claims on the same `Decision` topic without subsequent resolution                     | Quotes both speaker utterances; abstains from declaring agreement                     |
| `missing_required_participant` | Decision topic matches a team/service whose required reviewer (from §13 policy) is absent from meeting roster | Cross-checks active roster against read-only team/CODEOWNERS metadata (`as_of`)       |
| `unsupported_assumption`       | `Assumption` node linked via `ASSUMES -> Decision` with zero `SUPPORTED_BY -> Evidence`                       | Marked `status=inferred`, `kind=alert`, `[Inferred]` label required                   |
| `conflicting_data`             | Spoken metric/status contradicts retrieved read-only Jira/GitHub/monitoring snapshot                          | Emits conflict alert citing exact `as_of` record; blocks `verified` claim assertion   |
| `no_owner`                     | Agreed `Decision` or `Commitment` has empty `OWNED_BY` edge (`owner_unassigned`)                              | Triggers `owner_unassigned` nudge; no external ticket created without human selection |
| `no_required_approval`         | Proposed deployment/escalation lacks `Approval` node from `Decision.required_approvers`                       | Surfaces Trust Gate requirement (`approval_required`); blocks automated dispatch      |

### 3.4 §13 Trust Gate Declarative Policy Engine

§13 transitions from ad-hoc confirmation prompts to a **declarative tenant policy schema** evaluated deterministically before any §14 Connector call:

- **Action Classes**:
  - `read_only`: Jira/Linear/GitHub/Slack/Confluence/Notion fetch & citation (`context_cache` population; no source code blob indexing per `engineering-pack.md` §4.1).
  - `manager_approval`: Creating/updating Sprint tickets, posting non-destructive PR review summaries, scheduling review reminders (`requires team lead / engineering manager approval`).
  - `ops_approval`: Production deployment triggers, incident severity changes, rollback invocations, branch/release gate transitions (`requires on-call / release owner / SRE approval`; deferred `finance_approval` placeholder preserved in schema only for future Financial `SPEC-ONLY` vertical).
- **Policy Rule Matrix**: Configured per tenant (`team`, `environment`/`stage`, `severity` or numeric impact ceiling), specifying:
  1. Permitted read-only data sources per team (`github`, `jira`, `linear`, `slack`, `confluence`, `notion`).
  2. Permitted acting agent IDs (`pre_meeting_agent`, `live_agent`, `post_meeting_agent`, `outcome_tracker`).
  3. Required approver roles (`required_approvers`) and expiration TTL.
- **Immutable Audit Invariant**: Every Trust Gate policy evaluation (`allowed`, `denied`, `approval_pending`, `approved`, `rejected`) MUST write an append-only record to Neon `audit_events` (`audit_event_id`) linked onto the Graph `Approval` node before §14 invokes any external API.

### 3.5 New §22 — Outcome Tracker

MeetMind AI adds **§22 Outcome Tracker** to close the loop from engineering meetings to production impact:

1. **Decision Capture Contract**: Every `Decision` written to §8 carries `expected_outcome: {metric, target, review_date, owner}` alongside `source_event_ids`.
2. **Scheduled Verification via §14 Read-Only Connectors**: At/after `review_date`, §22 queries read-only connectors to trace the 5-hop engineering lineage:
   `Decision` → `Action` (`EXECUTED_AS`) → `Entity(Ticket)` → `Entity(PullRequest)` → `Entity(Deployment)` → `Outcome(metric vs target)` (`RESULTED_IN`).
3. **Graph Persistence & Pre-Meeting Recall**: Recorded `Outcome` nodes (`met | missed | pending | indeterminate`, `actual_value`, `evaluated_at`) persist to §8 (scoped by `tenant_id` and `restricted`) and feed §10 Pre-Meeting Briefs so future design reviews see whether past estimates and SLA fixes actually hit their targets.
